# 개정 규약 (amend)

`plan.md` 의 요구사항을 **추가·개정·철회**하는 공통 절차. `cruise:plan`(개정 모드)과
`cruise:build`(STEP 0 세미플랜)가 이 규약을 따른다. 산출물 스키마는 `CONTRACT.md` §4a.

원칙: **전체 재작성이 아니라 부분 수정.** 손대지 않은 줄은 바이트 단위로 보존한다.

---

## 1. 경계 판정 — 무엇을 대상으로 보는가

우선순위대로 하나만 택한다.

| # | 조건 | 대상 |
|---|------|------|
| 1 | 스킬 인자에 **문장**이 있음 | 그 인자가 확정 지시 |
| 2 | 인자 없음 | 대화에서 **마지막 스킬 호출**(그 스킬의 `완료…` 출력) **이후** 발화 |
| 3 | 호출 지점을 찾을 수 없음 (세션 교체·컨텍스트 압축) | 남은 대화 전체. 단 `## 개정 이력` 의 근거 인용과 대조해 **이미 반영된 것을 제외** |

> **예외 — 이슈 키 단독은 확정 지시가 아니다.** 인자가 `SPT-4200` 처럼 `[A-Z]+-\d+` 하나뿐이면
> 그것은 **대상 이슈 지정**이며 요구사항 지시가 아니다. 이때 근거는 명세 + 대화(2·3단계)로 판정한다.

대상 발화 중 **확정 지시만** 취한다. 질문·가정·탐색("~하면 어때?", "~할까?"), 이미 철회된 논의,
결론이 나지 않은 비교는 제외하고 `### 미지수` 로 보낸다.

---

## 2. 판별 4분기

**먼저 기존 R 목록과 `## 개정 이력` 을 읽는다.** 그 다음 요청 항목마다:

```
기존 R 하나의 문장을 고치면 표현되나?        → revise (문장)
R 은 그대로고 구현 방식·범위만 바뀌나?        → revise (작업 항목 · 파일 · 검증)
어느 R 에도 붙지 않나?                       → add
더 이상 필요 없나?                           → withdraw
확정되지 않았나?                             → 미지수
```

- **중복 금지**: 의미가 기존 R 과 겹치는 요청은 `add` 하지 않는다 (`revise` 또는 제외)
- **연쇄 자문 1회**: *이 추가가 기존 R 의 구현을 바꾸는가?* 바꾼다면 `add` 와 함께 그 R 의
  `revise` 도 선언한다

---

## 3. 적용 방법 (부분 수정)

| 연산 | 적용 |
|------|------|
| `add` | 요구사항 줄 append (ID = **현재 최대 + 1**, 미체크). 작업 항목·`생성/수정 파일`·검증 표 행을 함께 추가. **검증 방법 없는 요구사항은 추가하지 않는다** |
| `revise` | 해당 줄만 치환 + **체크 해제**. 구현 방식이 바뀌면 `생성/수정 파일` 도 갱신 |
| `withdraw` | 줄을 지우지 않고 `(철회: 사유)` 접미. 관련 작업 항목은 제거 |
| 미지수 | `### 미지수` 에 한 줄 추가. 결론 시 R 로 승격하고 그 줄 제거 |

모든 연산 후 `## 개정 이력` 에 한 줄 append (형식은 CONTRACT §4a).
`phases_count`·`updated` frontmatter 를 갱신한다.

**빈 선언** — `add`·`revise`·`withdraw`·미지수가 모두 비면 **파일을 쓰지 않고 archive 도 하지 않고**
`변경 없음` 한 줄 출력 후 [STOP].

---

## 4. 게이트 — 조건부

| 상황 | 게이트 |
|------|--------|
| `add` 만 (기존 R 을 건드리지 않음) | **없음** — 바로 진행 |
| `revise` · `withdraw` 포함 | **있음** — 이미 만든 것을 되돌리므로 |
| Plan Mode 활성 | `AskUserQuestion` 대신 **ExitPlanMode** 로 제시 (이중 승인 금지) |
| plan 의 최초 작성 | **있음** — 요구사항 전체가 처음 정해지는 시점 |

### 표시 형식

```
반영할 내용 — 진행할까요?
  추가  R6  카테고리 필터 칩 — 선택 시 목록 필터링
            근거: "카테고리별로 걸러지게"
            Phase 3 신규 · src/branded/FilterChips.tsx (new)
            검증: 칩 선택 시 목록 갱신 — `npm test filter`
  개정  R1  모바일 1열 / 태블릿 3열 / 데스크톱 4열
            근거: "태블릿 2열은 비어 보이네"
            → 체크 해제, 재구현 대상
  철회  R4  정렬 옵션 — 이번 스코프 제외
            근거: "정렬은 이번엔 빼자"
  미지수    다국어 지원 범위 — "나중에" (반영 안 함)
  제외      무한스크롤 → 버튼 — 결론 미확정으로 반영 안 함
  [진행] [수정] [plan으로] [취소]
```

**`미지수`·`제외` 줄을 반드시 표시한다.** 긴 대화에서 진짜 위험은 잘못 넣는 것보다
조용히 빠지는 것이다. 게이트가 없는 경우(순수 추가)에도 반영하지 않은 항목은 **종료 1줄에 남긴다.**

---

## 5. 근거 인용

| 출처 | 표기 |
|------|------|
| 대화 발화 | `("태블릿 2열은 비어 보이네")` — 원문 인용, 길면 앞부분만 |
| 스킬 인자 | `(인자: "필터 칩 키보드 탐색도 되게")` |
| Jira 명세 | `(task.md 명세)` / 암묵 도출은 `(암묵 요구사항 도출)` |

근거로 인용할 발화가 없으면 그 항목은 **선언하지 않는다.** 추측을 요구사항으로 만들지 않기 위한 장치다.

---

## 6. 에스컬레이션 (build 세미플랜 → plan)

세미플랜은 **기존 Phase 에 붙이거나 Phase 1개 추가**까지 감당한다. Phase 구조 재편·순서 변경·
전체 요구사항 재분해·task.md 명세 변경이 필요하면 amend 하지 않고 게이트에서 `[plan으로]` 를 제시한다.

```
세미플랜 범위를 넘습니다 — /cruise:plan 을 권합니다.
  이유: 새 Phase 3개 필요, Phase 2 경계 변경
  요청: "필터랑 정렬 다 넣고 검색 조건 저장까지"
  [plan으로] [취소]
```

---

## 7. 종료 출력

상태 한 줄 + **산출물 링크**. 요약·다음 액션 추천은 하지 않는다.

```
완료: 추가 R6 / 개정 R1 / 철회 R4
[plan.md](file:///Users/…/Documents/tasks/SPT-4152/plan.md)
```

- 반영하지 않은 항목이 있으면 같은 줄에: `완료: 추가 R6 / 미반영 2건 (태블릿 열 수, 접근성)`
- 경로는 `~` 가 아니라 `context.py` 가 해석한 **절대경로**
