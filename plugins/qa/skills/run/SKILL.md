# 화면 QA

요청받은 시나리오를 실제 브라우저에서 수행하고, 수락 기준마다 판정과 증거를 보고한다. 결과는 사람이 검토할 자료이고 머지 관문이 아니다.

## 시나리오 정하기

시나리오 양식은 아래와 같다.

```markdown
## QA 시나리오

- 대상: <로컬 | URL>
- 계정/역할: <테스트 계정·역할 | auth 저장 이름>

### 흐름

1. <사용자가 하는 일>

### 수락 기준

- <화면에서 눈으로 확인할 수 있는 결과>

### 사람이 확인할 것

- <렌더 테스트가 보지 못하는 것: 레이아웃, 겹침, 잘림, 색> (<화면>, <화면 폭>)
```

`### 수락 기준` 대신 `### 렌더 테스트로 확인할 것`을 쓰는 양식도 있다. 두 섹션의 항목을 모두 수락 기준으로 판정한다. `### 사람이 확인할 것`은 화면 모양을 보는 항목이라 스크린샷 증거를 꼭 붙인다.

시나리오 출처는 아래에서 처음 맞는 하나만 쓴다.

1. 사용자가 지목한 것: 문서 경로, 말로 가리킨 플랜, 이 대화에서 다룬 플랜, 요청에 직접 쓴 기대 결과. 플랜은 파일을 다시 읽어 쓴다.
2. 이번 작업의 계획에 있는 `## QA 시나리오`. 계획은 [계획 파일](${CLAUDE_PLUGIN_ROOT}/references/plan-file.md)의 「찾기」대로 찾는다.
3. 사용자가 계획이 없다고 확인하고 기대 결과도 주지 않으면 화면을 돌아보는 점검만 한다. PASS 판정을 하지 않고 에러와 화면 깨짐만 보고한다.

티켓은 읽지 않는다. 티켓 키는 플랜을 찾는 데만 쓴다. PR 본문은 출처로 쓰지 않는다. 플랜이 원본이고 PR 본문은 플랜에서 옮긴 결과물이다.

실행 전에 묻는 경우는 셋이다.

- 2번 후보가 둘 이상이면 고르지 말고 목록을 보여 준다.
- 계획 후보가 하나도 없으면(티켓 키를 받았든 아니든) 계획 경로나 확인할 기준을 알려 줄지, 점검만 할지 묻는다.
- 무엇을 확인할지 정할 수 없으면 묻는다.

대상을 안 주면 로컬 개발 서버로 본다. 수락 기준을 코드에서 만들지 않는다. 구현된 대로 동작하는지 확인하는 것이 되기 때문이다.

## 동작 범위

확인에 필요한 동작만 한다. 시나리오나 요청에 없는 생성·저장·삭제·초대·결제·권한 변경 버튼은 누르지 않는다. 이름 없는 버튼은 무엇인지 확인하기 전에는 누르지 않는다. 뷰포트는 1280×800과 390×844 둘 다 본다.

실행한 시나리오는 리포트에 남긴다. 플랜이 있었는데 섹션이 없었으면 추가할지 묻는다.

## 도구

```bash
ab() { npx -y agent-browser@0.41.2 --session qa-<실행 ID> "$@"; }
```

- 실행을 시작할 때 `<실행 ID>`를 한 번 정한다(예: `date +%H%M%S`). 이번 실행의 모든 호출에 같은 값을 쓰고, 다른 실행과 세션을 나눠 쓰지 않는다.
- 셸 상태는 명령 호출마다 초기화된다. 매 Bash 호출 앞에 이 함수를 다시 정의한다. 변수(`AB="npx ..."`)에 담으면 zsh가 단어로 나누지 않아 실행되지 않는다.
- 기본이 헤드리스다. 창을 띄우지 않고 마우스·키보드를 쓰지 않는다. 브라우저 프로필은 임시 폴더라 사용자 Chrome과 분리된다.
- 처음 쓸 때 `ab skills get core`로 명령을 확인한다.
- 스크린샷·로그는 스크래치패드(없으면 `$TMPDIR/qa-<날짜>`)에 둔다. 레포에 남기지 않는다.

## 로그인

비밀번호를 채팅으로 받거나 명령에 직접 쓰지 않는다. 사용자가 자기 터미널에서 저장하게 안내한다. `<이메일>`은 실제 주소로 바꿔야 한다고 함께 알린다.

```bash
npx -y agent-browser@0.41.2 auth save <이름> --url <로그인 URL> --username '<이메일>' --password-stdin
```

`ab auth login <이름>`은 입력만 하고 제출하지 않은 채 응답 없이 끝날 수 있다. 끝나면 먼저 URL과 화면으로 로그인됐는지 본다. 로그인 폼이 남아 있을 때만 활성화된 제출 버튼을 직접 누르고 다시 확인한다. 같은 이름의 버튼이 여럿이면 폼 안의 것을 고른다.

## 수행 루프

단계마다 관찰 → 행동 → 확인을 지킨다.

1. `ab snapshot -i`로 요소와 ref를 본다. 출력이 길면 `grep`·`head`로 필요한 부분만 읽는다.
2. ref로 행동한다(`click @e12`, `fill @e3 "..."`). ref가 없는 요소는 `find text|role|label ...`로 찾는다.
3. 결과를 확인한다. `✓ Done`은 성공 증거가 아니다. URL(`get url`), 바뀐 트리, `is visible`, 화면 텍스트 중 하나로 확인한다.
4. 페이지가 바뀌면 ref도 바뀐다. 다시 snapshot을 뜬다.
5. 고정 시간 대신 조건으로 기다린다(`wait --text`, `wait --url`, `wait <selector>`, `wait --load networkidle`).

이렇게 막히면 이렇게 한다.

| 증상 | 대응 |
| --- | --- |
| 클릭이 `Done`인데 아무 변화가 없다 | 한 번 재시도하고, 그래도 같으면 `ab close` 후 다시 연다. 리포트에 남긴다 |
| 닫은 모달이 트리에 남아 있다 | `is visible`로 판정한다 |
| 이름 없는 버튼·링크 | `get attr @ref href`, `get box`, 주변 순서, 스크린샷으로 정체를 확인한 뒤 누른다 |
| 다른 요소가 덮고 있다는 에러 | 덮은 요소(메뉴·배너·모달)를 먼저 닫는다 |
| `alert`·`confirm`·`prompt` | alert는 자동으로 닫힌다. 나머지는 `dialog status` 후 `dialog accept`·`dismiss` |
| 같은 단계에서 세 번 실패 | 멈추고 `BLOCKED`로 보고한다. 우회하려고 흐름에 없는 동작을 하지 않는다 |

## 체크포인트 증거

수락 기준을 판정하는 화면마다 두 뷰포트에서 남긴다.

```bash
ab set viewport 1280 800
ab screenshot <경로>/<체크포인트>-1280.png
ab set viewport 390 844
ab screenshot <경로>/<체크포인트>-390.png
```

- 로딩이 끝나고 판정 대상이 화면에 보이는 상태에서 찍는다. 기준과 상관없는 메뉴만 닫는다. 대상이 화면 아래에 있으면 그 위치로 스크롤하고, 필요하면 전체 화면 스크린샷(`--full`)을 따로 남긴다.
- 스크린샷은 직접 열어 본다. 깨짐·잘림·겹침·요소 누락을 본다. 1~2px 간격과 색상값은 판정하지 않는다.
- 가로 넘침: `ab eval 'document.documentElement.scrollWidth - document.documentElement.clientWidth'`가 0보다 크면 기록한다.
- 이름 없는 인터랙티브 요소: `snapshot -i`에서 이름 없는 `button`·`link`·`textbox`·`combobox` 수를 센다.

시나리오가 끝나면 `ab console`, `ab errors`, `ab network requests`에서 에러와 4xx·5xx를 모은다. 숨기지 않는다.

## 리포트

끝나면 `ab close`로 이번 세션만 닫고 아래 형식으로 보고한다.

```markdown
## QA 결과: <시나리오 이름>

대상 <URL> · 뷰포트 1280×800, 390×844 · 계정 <이름 또는 역할>
시나리오 출처 <문서 경로 | 요청 | 브랜치 변경 | 탐색 점검>

| 수락 기준 | 판정 | 증거 |
| --- | --- | --- |
| ... | PASS / FAIL / BLOCKED / UNAVAILABLE | 스크린샷 경로, URL, 관찰 |

### 발견한 문제

- <화면> <무엇이> <어떻게>. 재현 단계와 증거

### 확인 못 함

- <항목>과 이유
```

- 판정 기준: 두 뷰포트 중 하나라도 못 봤으면 PASS가 아니다. 앱이나 계정에 닿았는데 상태 때문에 막히면 `BLOCKED`, 브라우저·앱·계정 자체를 못 쓰면 `UNAVAILABLE`이다.
- 코드에서 원인을 찾았으면 추정인지 확인한 것인지 구분해 적는다.
- 스크린샷 경로는 절대경로로 쓴다.
